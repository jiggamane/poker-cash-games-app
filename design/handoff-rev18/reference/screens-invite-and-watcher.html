The poker club · build reference

The invite and watcher set · X2, C3, X1

Eighteen frames, drawn against rev 9 chrome. Every value is inline on the element — read the markup as the spec. Frames are 402 × 874 logical points; the 11px surround and 56px radius are the device bezel, not part of the screen. Written spec: 14-invite-and-watcher.md. Chrome per 09-navigation.md; tokens per 07-design-tokens.md.

The decision you put back to me — X1 is a push, not a root

Option 2. X1 is a pushed screen inside the app the reader already has, and there is no watcher install. Reasoning: the only thing that would make X1 a root is a phone with no book on it, and nothing else in the product needs one — an account buys you seeing the group from your own phone, which means a club root with your groups in it, which is the host root. Drawing a second root would mean specifying a first run, an idle state and an app name for a persona the data model does not have.

So: a share link opens the club root and pushes the night on top of it, and the back button returns to the club exactly as it does from Tonight. This supersedes the “Root, for a watcher’s install” row in 09-navigation.md. Depth is unaffected — club → night is one level, the same as club → Tonight.

One consequence worth naming rather than drawing: a reader with no app follows the same link in a browser. That is the same projection with the standalone header from X2 instead of Chrome A — no back button, because there is nothing behind it. Same body, same feed, same read-only footer. It is a container swap, not a screen.

X2 keeps its own classification: standalone, no chrome. It arrives from a link, the reader has not been anywhere, and there is nothing to go back to — so no chevron, no grabber, and deliberately no close.

The dead-code line is one string for four causes, and that is the point. Unknown, already spent, revoked and expired all render X2c: same title, same sentence, same single control, same layout. Nothing on the screen names the group, the host, the inviter or the code, because each of those is a fact a guesser would be paid for. Three build requirements go with it: one error shape on the wire (no cause code the client can read), a constant response time for all four (pad to the slowest, or the timing is the tell), and no cause in any log the client can reach. X1b is the same line in the share-link voice and I recommend it be governed by the same rule — a live-feed URL is as enumerable as an invite.

Everything marked PROPOSED is a draft I wrote to make the frame drawable, not a decision. Replace them and the layout does not move; the only two with geometry riding on them are the code length (ten characters, drawn as two groups of five) and the alphabet exclusion.

X2a

Checking the code

Standalone, no chrome · dark

The moment between landing and knowing. It exists because a code arriving on a link is checked on the server, and the alternative is a screen that flickers from nothing to a name.

  • No back, no close, no chevron. The reader arrived from a chat app; there is nowhere to return to and no gesture to advertise.
  • Progress is a 2px hairline at t.line with a 38% segment in the foreground, indeterminate. No spinner glyph, no logo.
  • Hold this screen a minimum of 400ms even when the answer is instant, or a good code reads as a flash of an error screen.
  • It resolves to exactly two places: X2b, or X2c. There is no third outcome — a network failure is retried behind this screen and only becomes X2c when the server has actually spoken.

X2d

Typing a code by hand

Standalone, no chrome · dark · shown beside X2a

Because a link is at the mercy of whatever chat app mangled it. Reachable from X2c and from the club root.

  • Ten characters, two groups of five, drawn as two 62px fields with a 10px gap. The second field is focused: 2px foreground border, caret 2 × 26.
  • 700 24px monospace, letter-spacing .14em, uppercased on entry. The alphabet excludes I, O, 0 and 1 — a code gets read down a phone, and those four are what gets misheard.
  • Primary is disabled until ten characters are in: card fill, muted label, no keyline (tokens: disabled is filled with no keyline). It does not go grey-on-tap; it goes to X2a.

  • A wrong code lands on X2c, not an inline field error. Same string, same screen, same four causes.
X2b

Ready — whose place it is

Standalone, no chrome · dark + light

The screen can name the person before anything is spent, because the code is bound to their member row. This is the whole argument for the per-player invite, so the drawing puts the name and the nights above the group.

  • Card order is deliberate: who you are (name, nights) then a hairline then what you are joining, then the plans. The nights come first because they are the surprise — the reader expects an empty account.
  • “Marek added you as Petr” — the name is 700 in the foreground inside a 400 14.5px muted sentence.
  • The three statements are the decided copy, one 5px dot each, 400 14.5px/1.45 foreground. Do not turn them into icons.
  • Nothing is claimed until the primary is tapped. Opening the link is idempotent and spends nothing; the code is burned on tap, not on arrival.
  • One list, sorted ascending: Free $0 → Regular $2.49 → Full $9.99. Free is row one and drawn as already yours — muted name and price, an outline check rather than the filled selection tick, and an INCLUDED tag. The two paid rows are upgrades from it. The plans do not gate the claim: Nothing paid is ticked by default. Free is the state the reader already has and the only marked row; both paid rows sit unselected, so the primary reads “Claim your place” and a plan is something the reader adds by tapping, never something they have to notice and remove. Ticking Regular for them would make the paid path the default act of claiming, which is the one thing this screen must not be. The claim is identical whichever row is selected — the member row attaches, the nights attach, and Free shows the last three. A claim that could fail on a card is a claim that loses the player. Claiming: the primary keeps its label, drops to opacity .55, and a 2px hairline progress bar sits under it. It is never a full-screen spinner — the card behind it is the thing being confirmed.
  • Done lands on the club root, this group already selected, no interstitial and no confirmation screen: the roster with their name in it is the confirmation. If a night is live, the root shows it live, which is the best possible landing.

Dead code

Standalone, no chrome · dark + light

Unknown, already spent, revoked and expired. One screen, one string, so somebody typing guesses learns nothing from which way it broke.

  • The four causes are indistinguishable by construction. Same title, same sentence, same control, same geometry, same response time. See the flag in the strings table for the three build requirements.
  • It names nothing: not the group, not the host, not the inviter, not the code that was tried. “whoever invited you” is doing security work, not tone work.
  • One control, and it is secondary — there is no primary act available here, and a filled button would imply there is.
  • Vertically centred with a 40px optical lift, not top-aligned: there is no chrome above it to hang from.
  • X1b is this screen in the share-link voice, and I recommend one rule governs both.

Sheet (Chrome B) over Players · dark + light

The per-player invite, which is the primary path. The link is the wrapper; the ten characters are what actually gets read down a phone or written on a beer mat, so they are the largest thing on the sheet.

C3d / C3e

The QR, and blocked

Sheet over Players · dark + light (QR) · dark (blocked)

A sheet over a sheet is not what happens; and the one thing in this app that cannot work offline says so before the host taps.

  • The QR replaces the sheet’s content in place. Same panel, same close, same 22px margins. Back to the invite is a text action, and swiping down or tapping the close leaves the whole sheet, not just the QR — which is why it must not be a second layer.
  • The QR block stays white in both themes, 250 × 250 with a 210px live area: a dark-inverted code is a scanning risk on cheap cameras. Raise screen brightness while it is shown and hold the screen awake.
  • The ten characters are repeated under it at 700 17px. A QR with no typable fallback is a dead end when the camera will not read it.
  • Blocked states before the tap, not after. Where the code would be there is a dashed placeholder saying why there is no code; the share chips are present but disabled, so the host can see what will be available rather than watching controls appear.
  • The offline sheet keeps Add by name only live and says so, because that path is local and is the honest answer to “I need this person in tonight’s ledger now”.
  • The signed-out twin is the same frame with the string in the table. Not drawn separately.

Push (Chrome A) · dark + light

N1/N2 with canWrite: false — same data, different projection. What is not just a projection: the watcher’s own position is pulled to the top, their own entries read in second person, and there is no action bar at all.

The screen ends in a statement instead of a control, which is the honest shape, and the band occupies the space a dock would — nothing floats in a void.

It is drawn because you asked for it, and it is drawn but not scheduled — the seam in §4 still holds, the policy module still returns true for everything in v1, and X2b ships with the plan block absent until membership is actually in a build. Names and prices follow the 12 Aug revision (Free / Regular $2.49 / Full $9.99), not §4’s older $4 / $9.

Why it earns its place here rather than on a P-screen: this reader has just been told they have four nights behind their name, and Free shows three. That is the only moment in the product where the gate is a number the reader has already read on the screen above it. Nothing paid is pre-ticked: a plan is added by tapping, not un-noticed and removed. Regular is the tier that answers the sentence, and the sentence is left to say so. On the sort order: ascending, and deliberately not the anchor-high pattern. Anchoring from $9.99 down works when a reader has no reference price; this one has $0, already owned and stated in the sentence above the list. Reading down from the ceiling puts the most expensive and least relevant row first and buries the plausible one in the middle. Ascending instead reads as current state → the step that fixes the sentence → the ceiling, which is also the order the reader’s own situation is in. With nothing paid pre-ticked, the sentence above the list carries the recommendation on its own — the reader’s own night count against the Free limit — and the order does the rest.

Two things it must not become: a wall, and a lie. Free is row one of the same list, marked as already included, and the claim is byte-identical whichever row is selected. If payment fails, the claim still happened.

Two logic questions the drawing exposed and cannot answer. (1) Does a per-player code expire? The 7-day expiry is specified for the group link only; C3a is drawn with no expiry line and a binding sentence instead. If per-player codes do expire, the sentence gains a clause and X2c gains a fourth cause it already covers. (2) What does Reset do to an already-claimed code? The claimed sheet is drawn with Reset live because S6 names it the only control there, but a claim has already attached the member row to an account — if reset is meant to detach that, it is an unbinding and needs its own confirmation copy; if it is not, the control should be disabled with the reason stated.
